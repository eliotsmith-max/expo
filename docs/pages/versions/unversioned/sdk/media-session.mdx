`expo-media-session` is the single owner of the app's audio session on iOS, audio focus on Android, and the lock screen and notification media controls on both. Media libraries, such as `expo-audio` and `expo-video`, request what they need from it instead of configuring the system themselves, so two libraries in one app do not fight over the session.

Use the JavaScript API to set the app-wide audio policy, keep the session active between sounds, and listen for interruptions and route changes. Library authors use the [native API](#for-library-authors).

## Configuration in app config

You can configure `expo-media-session` using its built-in [config plugin](/config-plugins/introduction/) if you use config plugins in your project ([Continuous Native Generation (CNG)](/workflow/continuous-native-generation/)). The plugin allows you to configure properties that cannot be set at runtime and require building a new app binary to take effect. If your app does **not** use CNG, then you'll need to manually configure the library.

On iOS, add the `audio` background mode to **Info.plist** if the app plays audio in the background:

```xml ios/[app]/Info.plist
<key>UIBackgroundModes</key>
<array>
  <string>audio</string>
</array>
```

On Android, declare the media playback service in **AndroidManifest.xml**. For background playback, add the foreground service type and permissions:

```xml android/app/src/main/AndroidManifest.xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK" />

<application>
  <service
    android:name="expo.modules.mediasession.service.MediaPlaybackService"
    android:exported="false"
    android:foregroundServiceType="mediaPlayback" />
</application>
```

The service reads its own declared `foregroundServiceType` to decide whether it can run in the foreground. Below Android 10 (API level 29), where service types do not exist, it follows the app's `FOREGROUND_SERVICE_MEDIA_PLAYBACK` permission instead.

## Usage

### Set the audio policy

The audio policy applies to every media library in the app. Fields that you leave out keep their current values.

```tsx
import { setAudioPolicyAsync } from 'expo-media-session';

await setAudioPolicyAsync({
  interruptionMode: 'doNotMix',
  shouldPlayInBackground: true,
});
```

On iOS, the promise rejects when the merged policy is invalid, for example `interruptionMode: 'duckOthers'` with `playsInSilentMode: false`. The error message says which field to change.

### Keep the session active between sounds

The module deactivates the session 1 second after the last library stops using it, except in `mixWithOthers` mode on iOS, where it never deactivates the session automatically. To keep it active for longer, for example between the clips of a game level, hold it with a key and release it with the same key:

```tsx
import { holdSession, releaseSession } from 'expo-media-session';

holdSession('level');
// ...
releaseSession('level');
```

The module releases every hold when the JavaScript runtime reloads.

### Listen for interruptions

```tsx
import { useEffect } from 'react';
import { addInterruptionListener } from 'expo-media-session';

export function useInterruptionLog() {
  useEffect(() => {
    const subscription = addInterruptionListener(event => {
      if (event.type === 'began') {
        console.log('Interrupted:', event.reason);
      } else {
        console.log('Interruption ended, can resume:', event.shouldResume);
      }
    });
    return () => subscription.remove();
  }, []);
}
```

`InterruptionReason` and `RouteChangeReason` can get new values, so handle unknown values with a default case.

### Web

On web, `setAudioPolicyAsync` stores the policy and does not change browser audio, and holds do nothing.

## For library authors

A media library uses the Swift and Kotlin API to get the session and to show Now Playing controls. Only this module writes the system state: `AVAudioSession` category and activation, Android audio focus, `MPNowPlayingInfoCenter`, `MPRemoteCommandCenter` targets, and the Media3 session service. A library that writes them directly breaks the other libraries in the app.

### Uses and holds

Begin a use when the player starts. The call returns at once, and the module activates the session or requests audio focus in the background. Keep the token while the audio plays.

```swift
import ExpoMediaSession

let use = MediaSessionManager.shared.beginUse(client: "my-player", requirements: SessionRequirements(mixing: .doNotMix))
try await use.activated()
// ...
use.end()
```

```kotlin
val use = MediaSessionManager.get(context).beginUse("my-player", SessionRequirements(mixing = MixingRequirement.DO_NOT_MIX))
use.awaitActivation()
// ...
use.close()
```

- On iOS, deinit ends a `SessionUse` or a `SessionHold`. On Android, call `close()`.
- `activated()` (iOS) and `awaitActivation()` (Android) wait for the first activation. They stay pending while writes are suspended, and on Android while a delayed focus grant is pending. They throw if the use ends first.
- Requirements can only make the policy stricter. The mixing order is `doNotMixPersistent`, `doNotMix`, `duckOthers`, then `mixWithOthers`.
- `hold(client:)` keeps the session active without requirements, like the JavaScript `holdSession`.

### Getting the session back

- `beginUse` and `hold` activate the session and request focus. The module also does this when it resumes writes, after an iOS media services reset, and after `mediaSessionInterruptionEnded(shouldResume: true)` on iOS.
- `update` and `setPolicy` reconfigure the session. On Android, a reconfigure for an active use requests focus again with the new attributes, which can win focus back after a transient loss.
- After a permanent focus loss, only `beginUse` and `hold` get the session back. End the use and begin a new one, for example when the user presses play.

### Observers

Add an observer with `addObserver`, and keep the returned `ObserverRegistration`. Every observer method has a default implementation, so implement only the events you need.

- Observer methods run on the coordinator queue (iOS) or the coordinator thread (Android). Switch to your own isolation before you touch UI or player state.
- Every `mediaSessionDucked(true)` gets exactly one `mediaSessionDucked(false)`. The Swift method is `mediaSessionDucked(_:)`, and the Kotlin method is `mediaSessionDucked(isDucked)`.
- Every `mediaSessionInterruptionBegan(reason:)` gets at most one `mediaSessionInterruptionEnded(shouldResume:)` before the next `mediaSessionInterruptionBegan(reason:)`. A permanent loss (`mediaSessionFocusLost(transient: false)` and `mediaSessionInterruptionBegan(reason:)`) may never get a `mediaSessionInterruptionEnded(shouldResume:)`.
- `mediaSessionInterruptionEnded(shouldResume: true)` is sent only when live uses remain and the session or focus is held again, or the policy no longer needs focus (`mixWithOthers`).
- `mediaSessionSilentModeChanged(isSilent:)` is Android only and reports the raw ringer state. Apply `playsInSilentMode` yourself.

### Suspended writes

`suspendWrites(reason:)` stops all writes to the session until the matching `resumeWrites()`. While writes are suspended:

- Android sends no focus events, and reports one net change after `mediaSessionDidResumeWrites()`. It can still send `mediaSessionDidFail(error, client)` when the media service or the foreground start fails, because the service is not a session write.
- iOS still sends `mediaSessionInterruptionBegan(reason:)`, `mediaSessionRouteChanged(reason:)`, and `mediaSessionServicesReset()`. It defers `mediaSessionInterruptionEnded(shouldResume:)` until writes resume. It sends no `mediaSession(didFail:client:)`, because it writes nothing.
- A library that mirrors an interrupted state rebuilds it from the events after `mediaSessionDidResumeWrites()`.

### Platform differences

- iOS can send `mediaSessionInterruptionBegan(reason:)` while no use is live. Android does not.
- A use that begins during an interruption is told about an ongoing transient loss on Android. On iOS, it gets no signal that it is interrupted.
- iOS does not report the "app was suspended" interruption reason.

### Now playing

Begin the session use first, then offer Now Playing. The module reads the live requirements when the offer arrives to decide whether the previous owner pauses.

```swift
let claim = MediaSessionManager.shared.offerNowPlaying(
  player,
  info: NowPlayingInfo(title: "Episode 12", duration: 1800, elapsedTime: 0, playbackRate: 1),
  commands: [.play, .pause, .togglePlayPause, .seek]
)
// On every play, pause, seek, rate, or metadata change:
claim.update(NowPlayingInfo(title: "Episode 12", duration: 1800, elapsedTime: 42, playbackRate: 0))
// When the player stops:
claim.withdraw(.ended)
```

- The newest offer goes on top. A pause keeps ownership. A withdraw removes that owner from anywhere in the stack.
- The previous owner is paused for the takeover, unless the effective interruption mode is `mixWithOthers`. When the newer owner withdraws, the previous owner resumes only if the takeover paused it.
- The defaults for `pauseForTakeover` and `resumeAfterTakeover` handle a `pause` and a `play` command.
- Commands go only to the top owner, and only for the kinds it offered. Do not offer `seek` for content that cannot seek. A live stream never shows `seek`.
- When you offer both skip and track commands, iOS shows next and previous instead of skip. iOS always answers commands with success.
- The module can write Now Playing at any time, for example when another owner withdraws. Keep `isPlaying` consistent with the `elapsedTime` and `playbackRate` of your last update.
- Owner callbacks run on the coordinator queue or thread. On iOS, the module switches to the main thread for the system writes, in order.
- On iOS, deinit of a `NowPlayingClaim` withdraws it. On Android, call `close()`.
- On Android, the owner is driven by the `NowPlayingInfo` you send. An owner that implements `MediaPlayerOwner` exposes its Media3 `Player` instead.
